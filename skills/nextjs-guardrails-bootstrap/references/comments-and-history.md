# Code comments, change history and public-safe content

Shared by every `*-guardrails-bootstrap` skill. The skill's `SKILL.md` keeps only
the rules; this file holds the detail. Install it in the target project as part of
`AGENTS.md` (short form) and `docs/engineering/HISTORY.md` (the log).

## Why this exists

Agents that are told to keep code "understandable" but are given no place for
history write it into the code: multi-paragraph docblocks explaining how a bug was
found, what the previous version did, which alternative was rejected and why.
Each comment is reasonable; together they bury the code and go stale on the next
change. Git history and docs are better homes for that text.

## Comment rules (for the target project's `AGENTS.md`)

1. A comment is at most 1–2 lines and says **why**, never **what** the code
   already says.
2. Only comment what a competent reader would get wrong: a non-obvious ordering,
   a workaround, a security/tenant boundary, a contract with an external system.
3. No history in code: no "previously…", "we changed this because…", "bug found
   on…", incident narratives, rejected alternatives or dates. That goes to
   `HISTORY.md`, `DECISIONS.md` or the commit message.
4. When the why needs more than two lines, write one line plus a stable
   reference: `// Signed URL, not a stored token. See DECISIONS.md#d-012`.
5. Reference by stable ID (`D-012`, `H-031`), never by line number or by a doc
   that may be renamed.
6. Type annotations, API docblocks consumed by tools (PHPDoc types, JSDoc/TSDoc
   used by the IDE, GDScript `##` exported docs) and license headers are not
   narrative; keep them, keep them terse.
7. A comment is not a guard. If a rule matters ("admin only", "must run after X"),
   enforce it in code or a test, then comment in one line if still needed.
8. When touching code with an existing long comment, do not rewrite unrelated
   comments. Shorten only the ones in the diff, moving useful history to the
   docs.

## Where longer explanations go

| Content | Home |
|---|---|
| Durable architectural choice and its trade-off | `DECISIONS.md` (entry `D-NNN`) |
| Bug fix, regression, incident, workaround and its cause | `HISTORY.md` (entry `H-NNN`) |
| How a module/flow works end to end | `SYSTEM_MAP.md` or `docs/engineering/notes/<area>.md` |
| What changed in this commit and why | commit message / PR description |
| Commands, environments, how to verify | `TESTING.md` |

Do not create `notes/` files preemptively; create one only when a module really
needs more than `SYSTEM_MAP.md` gives it.

## `HISTORY.md` format

Newest first. Short entries; this is an index of non-obvious fixes, not a changelog
of every commit.

```markdown
## H-031 — 2026-01-14 — Invite link opened the wrong screen

**Symptom:** invited users landed on the dashboard instead of setting a password.
**Cause:** one signed route served both the invite and the "resume" flow.
**Fix:** separate route for invites (`InviteLinks::for`).
**Guard:** `tests/Feature/InviteLinkTest.php`.
**Code refs:** comment `See HISTORY.md#h-031` in `InviteLinks`.
```

Add an entry when a fix encodes knowledge that the code alone does not show and
that someone could undo by "simplifying". Skip trivial fixes.

## `DECISIONS.md` IDs

Give each entry a stable ID so code can point at it:

```markdown
## D-012 — 2026-01-10 — Signed URLs instead of stored invitation tokens
```

## Public-safe content (code, comments, docs, fixtures, commit messages)

Never write into the repository:

- personal data: real names, emails, phone numbers, addresses, account IDs of
  the owner, teammates or customers (use `user@example.com`, `+1 555 0100`);
- real customer records copied from production into fixtures, docs or tests;
- machine-local paths (`/Users/<name>/…`, `C:\Users\…`, home-directory skill
  or config paths);
- AI-tool metadata: model names, "generated by <assistant>", agent branch names,
  session IDs, prompts. The code is the project's, not the tool's;
- internal hostnames, tokens, keys or credentials, even "temporary" ones.

Before a meaningful commit, scan the diff for these. If one already landed in a
public repository, removing it in a new commit is not enough: it stays in the
history and in published packages. Flag it to the owner.

## Existing comment debt (optional follow-up, not part of the bootstrap)

The bootstrap does not touch product code. During the Phase 1 audit, report
roughly how many multi-line narrative comment blocks exist and where they
concentrate. If the owner wants a cleanup, do it as a separate comment-only
change:

1. move history worth keeping to `HISTORY.md` / `DECISIONS.md` with IDs;
2. shorten comments to 1–2 lines, adding `See …#id` where history moved;
3. prove no code changed (AST/token diff, `php -l`, `tsc --noEmit`, tests);
4. one commit, comment-only, easy to review and revert.
